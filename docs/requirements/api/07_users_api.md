# Customer API Contract Specification — покупатели

## Общая структура

User response содержит `id`, `full_name`, `email`, `created_at`. List response содержит `items` и `count`.

## POST /users

### Назначение

Создать покупателя.

### Ответственность

Провалидировать данные, обеспечить уникальность email и сохранить User.

### Источник данных

Request body; сохранённая запись — `customer_db`.

### HTTP Method

`POST`.

### URL

`/users`.

### Path Parameters

Не применяется.

### Query Parameters

Не применяется.

### Request Body

Обязательный JSON: `full_name`, `email`.

### Response

HTTP 201 с созданным User.

### Структура ответа

Входные поля плюс серверные `id` и `created_at`.

### Используемые модели

Контракт создания/чтения User, ORM `User`.

### Бизнес-правила

Email уникален в customer DB.

### Проверки валидации

`full_name`: 3–255 символов; `email`: валидный email; оба поля обязательны.

### Ошибки

- 400 `validation_error` — неверное/неполное тело.
- 409 `user_conflict` — email уже существует.
- 500 `internal_error`.

### Побочные эффекты

Создаёт строку User.

### Kafka события

Не применяется.

### Изменяемые таблицы

`users`: INSERT.

### Acceptance Criteria

- Валидный уникальный email создаёт одну запись и возвращает 201.
- Дубликат email не создаёт User и возвращает 409.

### QA Checklist

- Проверить обязательность, длины full name и email format.
- Проверить duplicate email и согласованность API/DB.
- Проверить отсутствие Kafka events.

### Ограничения

Нет пароля, auth, ролей, телефона или endpoint изменения/удаления User. Case-insensitive уникальность email не определяется кодом.

## GET /users

### Назначение

Получить всех покупателей.

### Ответственность

Прочитать User rows по возрастанию ID и сформировать список.

### Источник данных

Таблица `users` в `customer_db`.

### HTTP Method

`GET`.

### URL

`/users`.

### Path Parameters

Не применяется.

### Query Parameters

Не применяется.

### Request Body

Не применяется.

### Response

HTTP 200.

### Структура ответа

`items` — User по ID; `count` — длина массива.

### Используемые модели

ORM `User`, публичный User, список User.

### Бизнес-правила

Возвращаются все User.

### Проверки валидации

Не применяется.

### Ошибки

Специализированные 4xx не определены; возможен 500 `internal_error`.

### Побочные эффекты

Не применяется.

### Kafka события

Не применяется.

### Изменяемые таблицы

Не применяется; `users` только читается.

### Acceptance Criteria

- Пустая таблица возвращает `items=[]`, `count=0`.
- Непустой список отсортирован по ID, count совпадает с длиной.

### QA Checklist

- Проверить пустой/непустой список, порядок и count.
- Проверить отсутствие связанных cart/favorite/order данных.

### Ограничения

Нет пагинации, фильтрации и сортировки по параметрам.

## GET /users/{user_id}

### Назначение

Получить User по ID.

### Ответственность

Вернуть существующего покупателя либо контролируемую ошибку.

### Источник данных

Таблица `users`.

### HTTP Method

`GET`.

### URL

`/users/{user_id}`.

### Path Parameters

`user_id` — integer PK; дополнительное ограничение `>0` не задано.

### Query Parameters

Не применяется.

### Request Body

Не применяется.

### Response

HTTP 200 с User.

### Структура ответа

Полное публичное представление User.

### Используемые модели

ORM `User`, публичный User.

### Бизнес-правила

User должен существовать.

### Проверки валидации

Path должен преобразовываться в integer.

### Ошибки

- 400 `validation_error` — нечисловой path.
- 404 `user_not_found` — User отсутствует.
- 500 `internal_error`.

### Побочные эффекты

Не применяется.

### Kafka события

Не применяется.

### Изменяемые таблицы

Не применяется; `users` только читается.

### Acceptance Criteria

- Существующий ID возвращает соответствующего User.
- Отсутствующий ID возвращает 404 в error envelope.

### QA Checklist

- Проверить существующий, отсутствующий, нулевой/отрицательный и нечисловой ID.
- Проверить отсутствие связанных сущностей в ответе.

### Ограничения

Не возвращает favorites, cart или orders.
