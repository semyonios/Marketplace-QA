# Supplier API Contract Specification — поставщики

## Общие структуры

Supplier в ответе содержит: integer `id`; строки `full_name`, нормализованный `phone_number`, `email`, `city`; календарную `birth_date`; `created_at` и `updated_at` с датой и временем. Список содержит массив `items` и integer `count`. Ошибка содержит объект `error` с `code` и `message`.

## POST /suppliers

### Назначение

Создать поставщика.

### Ответственность

Валидировать и нормализовать данные, обеспечить уникальность email/телефона, сохранить supplier и инициировать событие создания.

### Источник данных

Тело HTTP-запроса; сохранённая запись и timestamps — `supplier_db`.

### HTTP Method

`POST`.

### URL

`/suppliers`.

### Path Parameters

Не применяется.

### Query Parameters

Не применяется.

### Request Body

Обязательный JSON: `full_name`, `phone_number`, `email`, `birth_date`, `city`.

### Response

HTTP 201 с созданным Supplier.

### Структура ответа

Supplier со всеми входными полями, серверным `id`, `created_at`, `updated_at`; телефон возвращается нормализованным.

### Используемые модели

Контракт создания Supplier, публичное представление Supplier, ORM-сущность `Supplier`.

### Бизнес-правила

Email и телефон уникальны. Телефон сохраняется в форме `+7` и десять цифр.

### Проверки валидации

`full_name`: 3–255 символов; `phone_number`: до 30 символов до нормализации и распознаваемый российский номер; `email`: валидный email; `birth_date`: дата; `city`: 2–120 символов. Все поля обязательны.

### Ошибки

- 400 `validation_error` — неверное или неполное тело.
- 409 `supplier_conflict` — email или нормализованный телефон уже существует.
- 500 `internal_error` — необработанная ошибка.

### Побочные эффекты

Добавляет строку supplier и timestamps; пишет warning/error logs при ошибках.

### Kafka события

После commit публикуется `SUPPLIER_CREATED` в `supplier-events`, key = supplier ID, payload = публичное представление Supplier, `event_version=1`.

### Изменяемые таблицы

`users`: INSERT.

### Acceptance Criteria

- Валидное уникальное тело создаёт одну запись и возвращает 201 с ID/timestamps.
- Номер с префиксом `8` сохраняется и возвращается с `+7`.
- Дубликат email или телефона не создаёт запись и возвращает 409.
- Событие формируется только после успешного commit.

### QA Checklist

- Проверить минимальные/максимальные длины строк и обязательность полей.
- Проверить email и варианты телефона с разделителями, `7`, `+7`, `8`.
- Проверить конфликты email и телефона отдельно.
- Сопоставить API-ответ, строку БД и Kafka payload.

### Ограничения

Возраст, уникальность имени и города не проверяются. Подтверждение доставки Kafka не ожидается.

## GET /suppliers

### Назначение

Получить всех поставщиков.

### Ответственность

Прочитать supplier rows, отсортировать по ID и сформировать list response.

### Источник данных

Таблица `users` в `supplier_db`.

### HTTP Method

`GET`.

### URL

`/suppliers`.

### Path Parameters

Не применяется.

### Query Parameters

Не применяется.

### Request Body

Не применяется.

### Response

HTTP 200.

### Структура ответа

`items` — Supplier в порядке возрастания ID; `count` — длина возвращённого массива.

### Используемые модели

Публичное представление Supplier, список Supplier, ORM-сущность `Supplier`.

### Бизнес-правила

Возвращаются все существующие supplier rows.

### Проверки валидации

Не применяется.

### Ошибки

Специализированные 4xx не определены; возможен 500 `internal_error`.

### Побочные эффекты

Не применяется.

### Kafka события

Не применяется.

### Изменяемые таблицы

Не применяется; `users` только читается.

### Acceptance Criteria

- Пустая БД возвращает 200, пустой `items` и `count=0`.
- Непустой результат отсортирован по ID, а `count` равен числу элементов.

### QA Checklist

- Проверить пустой и непустой список.
- Проверить порядок ID и согласованность `count`.
- Проверить отсутствие Kafka-событий и изменений БД.

### Ограничения

Пагинация, фильтрация и параметризованная сортировка отсутствуют.

## GET /suppliers/{supplier_id}

### Назначение

Получить одного поставщика по ID.

### Ответственность

Найти supplier row и вернуть публичное представление либо контролируемую ошибку.

### Источник данных

Таблица `users` в `supplier_db`.

### HTTP Method

`GET`.

### URL

`/suppliers/{supplier_id}`.

### Path Parameters

`supplier_id` — integer, интерпретируемый как PK. Дополнительное ограничение `> 0` не задано.

### Query Parameters

Не применяется.

### Request Body

Не применяется.

### Response

HTTP 200 с Supplier.

### Структура ответа

Полное публичное представление Supplier.

### Используемые модели

Публичное представление Supplier, ORM-сущность `Supplier`.

### Бизнес-правила

Supplier должен существовать.

### Проверки валидации

Path parameter должен преобразовываться в integer.

### Ошибки

- 400 `validation_error` — path не является integer.
- 404 `supplier_not_found` — запись отсутствует.
- 500 `internal_error` — необработанная ошибка.

### Побочные эффекты

Не применяется.

### Kafka события

Не применяется.

### Изменяемые таблицы

Не применяется; `users` только читается.

### Acceptance Criteria

- Существующий ID возвращает 200 и соответствующую запись.
- Отсутствующий integer ID возвращает 404 в едином формате ошибки.

### QA Checklist

- Проверить существующий, отсутствующий, нулевой/отрицательный и нечисловой ID.
- Проверить отсутствие изменений БД и событий.

### Ограничения

Не возвращает связанные товары поставщика.

## PUT /suppliers/{supplier_id}

### Назначение

Изменить поля существующего поставщика.

### Ответственность

Применить только переданные поля, повторно проверить формат/уникальность и опубликовать обновлённое состояние.

### Источник данных

Path и request body; текущая/обновлённая запись — `supplier_db`.

### HTTP Method

`PUT`.

### URL

`/suppliers/{supplier_id}`.

### Path Parameters

`supplier_id` — integer PK; ограничение `> 0` не задано.

### Query Parameters

Не применяется.

### Request Body

JSON с любым подмножеством `full_name`, `phone_number`, `email`, `birth_date`, `city`. Поля optional; пустой объект принимается.

### Response

HTTP 200 с итоговым Supplier.

### Структура ответа

Полное состояние после операции, включая неизменённые поля и timestamps.

### Используемые модели

Контракт обновления Supplier, публичное представление Supplier, ORM-сущность `Supplier`.

### Бизнес-правила

Supplier должен существовать; email/телефон остаются уникальными; телефон нормализуется.

### Проверки валидации

Переданные поля имеют те же форматы и длины, что при создании. Явный `null` проходит входную optional-схему, но противоречит NOT NULL колонкам и специализированно не обрабатывается.

### Ошибки

- 400 `validation_error` — неверный path/body.
- 404 `supplier_not_found` — supplier отсутствует.
- 409 `supplier_conflict` — нарушение уникальности или иное IntegrityError при commit, включая возможный NOT NULL conflict.
- 500 `internal_error` — необработанная ошибка.

### Побочные эффекты

Обновляет переданные поля и DB-managed `updated_at` при фактическом UPDATE.

### Kafka события

После успешного commit публикуется `SUPPLIER_UPDATED` с полным итоговым Supplier, key = ID, `event_version=1`. Пустой объект также проходит путь commit/publish.

### Изменяемые таблицы

`users`: UPDATE при наличии фактических изменений.

### Acceptance Criteria

- Существующий supplier принимает частичное тело и возвращает полное итоговое состояние.
- Непереданные поля сохраняются.
- Конфликт уникальности возвращает 409 без подтверждённого изменения.
- Успешная операция инициирует `SUPPLIER_UPDATED`.

### QA Checklist

- Обновить каждое поле отдельно и комбинацией.
- Проверить пустой JSON и явные null.
- Проверить нормализацию телефона и оба уникальных конфликта.
- Проверить отсутствующий/нечисловой ID, timestamps и Kafka payload.

### Ограничения

Несмотря на HTTP method PUT, реализация имеет семантику частичного обновления. Явный null может приводить к 409 через общий IntegrityError.

## DELETE /suppliers/{supplier_id}

### Назначение

Физически удалить поставщика без связанных товаров.

### Ответственность

Проверить существование и отсутствие Product, удалить supplier и опубликовать снимок удалённой записи.

### Источник данных

Таблицы `users` и `products` в `supplier_db`.

### HTTP Method

`DELETE`.

### URL

`/suppliers/{supplier_id}`.

### Path Parameters

`supplier_id` — integer PK.

### Query Parameters

Не применяется.

### Request Body

Не применяется.

### Response

HTTP 204 без тела.

### Структура ответа

Не применяется.

### Используемые модели

ORM `Supplier`, ORM `Product`, публичное представление Supplier для Kafka payload.

### Бизнес-правила

Supplier должен существовать и не иметь ни одного связанного товара. Архивный товар также остаётся Product и блокирует удаление.

### Проверки валидации

Path parameter должен быть integer.

### Ошибки

- 400 `validation_error` — неверный path.
- 404 `supplier_not_found` — supplier отсутствует.
- 409 `supplier_has_products` — найден хотя бы один Product с этим supplier ID.
- 500 `internal_error` — необработанная ошибка.

### Побочные эффекты

Физически удаляет строку `users` после формирования снимка.

### Kafka события

После commit публикуется `SUPPLIER_DELETED` с данными удалённого Supplier, key = ID, `event_version=1`.

### Изменяемые таблицы

`users`: DELETE. `products`: только проверка существования.

### Acceptance Criteria

- Supplier без Product удаляется, возвращается 204, последующее чтение даёт 404.
- Supplier с любым связанным Product не удаляется и получает 409.
- Успешное удаление инициирует событие со снимком до удаления.

### QA Checklist

- Удалить supplier без товаров.
- Проверить блокировку для активного и архивного товара.
- Проверить отсутствующий/нечисловой ID, пустое тело 204 и Kafka payload.

### Ограничения

Каскадное удаление товаров не выполняется. Подтверждение доставки события не контролируется.
