# Анализ проекта Marketplace-QA

## 1. Основание и границы анализа

Анализ выполнен по состоянию ветки `fix2_11.04`, коммит `265cd8c166fd703c4c35db0c6439029655a5c05b`. Источники: корневой `README.md`, `docker-compose.yml`, Dockerfile и зависимости трёх приложений, весь Python-код моделей, схем, API, обработчиков ошибок, Kafka producer/consumer, а также `.postman/resources.yaml`.

В репозитории отсутствуют автоматические тесты, миграции БД, отдельные OpenAPI-файлы, AsyncAPI/Avro/JSON Schema для событий, диаграммы, CI-конфигурация и код внешних интеграций. Поэтому ниже описано наблюдаемое поведение реализации, а не предполагаемое целевое поведение.

## 2. Назначение проекта

Marketplace-QA — локальный демонстрационный marketplace для ручной QA-практики. Система моделирует две предметные области:

- управление поставщиками, товарами, складами и складскими остатками;
- работу покупателя с локальным каталогом, избранным, корзиной и заказами.

Проект демонстрирует HTTP API, асинхронный обмен через Kafka, раздельное хранение данных сервисов и eventual consistency. Аутентификация, авторизация, оплата, доставка и внешние интеграции в коде отсутствуют.

## 3. Структура репозитория

| Объект | Содержание |
|---|---|
| `supplier-service/` | FastAPI API поставщика, supplier-модели, producer трёх типов событий и consumer заказов |
| `customer-service/` | FastAPI API покупателя, customer-модели, локальная проекция каталога, producer заказов и consumer каталога/остатков |
| `audit-consumer/` | Фоновый consumer событий поставщика и их запись в supplier БД |
| `docker-compose.yml` | Локальная топология из восьми контейнеров и двух volumes |
| `README.md` | Инструкция запуска, обзор API, ручные и негативные сценарии, правила и ограничения |
| `.postman/resources.yaml` | Ссылки рабочего пространства на коллекции Postman Cloud; сами коллекции в репозитории отсутствуют |

Каждое Python-приложение собирается из `python:3.12-slim`. Supplier и customer запускаются через Uvicorn, audit — как модуль Python.

## 4. Компоненты и ответственность

### 4.1. `supplier-service`

Источник истины для:

- поставщиков;
- товаров и их признаков активности/архивности;
- складов;
- остатков товара на каждом складе;
- агрегированного остатка товара.

Сервис предоставляет CRUD-подобный HTTP API, записывает данные в `supplier_db`, публикует изменения поставщиков, товаров и остатков в Kafka и потребляет события созданных заказов. После события заказа он уменьшает остатки по складским строкам и публикует новый агрегированный остаток.

При старте сервис создаёт отсутствующие таблицы и при необходимости добавляет в `products` поля `is_active` и `is_archived`. Kafka consumer запускается в daemon-thread внутри процесса API.

### 4.2. `customer-service`

Отвечает за:

- покупателей;
- локальную проекцию каталога товаров;
- избранное;
- корзину;
- заказы и позиции заказов.

Сервис хранит данные в `customer_db`. Каталог не редактируется customer API: он заполняется событиями supplier-service и полной HTTP-синхронизацией с `GET supplier-service:8000/products` при старте. При создании заказа customer-service сохраняет заказ локально, очищает всю корзину пользователя и публикует по одному Kafka-событию на каждую агрегированную позицию заказа.

При старте сервис создаёт таблицы, выполняет ограниченную адаптацию старой схемы `orders`, добавляет продуктовые флаги при их отсутствии, запускает один consumer двух Kafka-топиков и делает полную HTTP-синхронизацию каталога.

### 4.3. `audit-consumer`

Отдельный процесс без HTTP API. Потребляет только события поставщиков из `supplier-events` и добавляет каждое событие в таблицу `user_events` базы `supplier_db`. Он не потребляет события товаров, остатков или заказов.

### 4.4. Инфраструктурные компоненты

- `supplier-postgres` — PostgreSQL 16 Alpine, БД `supplier_db`, внешний порт `5432`.
- `customer-postgres` — PostgreSQL 16 Alpine, БД `customer_db`, внешний порт `5433`.
- `kafka-broker` — Apache Kafka 4.2.0, одновузловой KRaft broker/controller, порт `9092`, автоматическое создание топиков включено.
- `kafka-ui` — веб-интерфейс к локальному Kafka-кластеру, порт `8080`.

## 5. Взаимодействие компонентов

| Источник | Канал | Получатель | Назначение |
|---|---|---|---|
| Клиент | HTTP `:8000` | supplier-service | Управление supplier-доменом |
| Клиент | HTTP `:8001` | customer-service | Каталог и customer-сценарии |
| supplier-service | `supplier-events` | audit-consumer | Аудит создания, изменения и удаления поставщика |
| supplier-service | `product-events` | customer-service | Создание и обновление локальной проекции товара |
| supplier-service | `product-stock-events` | customer-service | Обновление агрегированного остатка проекции |

Прямого доступа одного доменного сервиса к БД другого нет. Исключение на уровне владения данными: audit-consumer использует ту же `supplier_db`, что и supplier-service.

## 6. Модель данных

### 6.1. `supplier_db`

#### `users` (`Supplier`)

Несмотря на имя таблицы `users`, модель называется `Supplier`.

| Поле | Тип/ограничение | Смысл |
|---|---|---|
| `id` | PK integer | Идентификатор поставщика |
| `full_name` | varchar(255), not null | Полное имя |
| `phone_number` | varchar(30), unique, not null | Нормализованный телефон |
| `email` | varchar(255), unique, indexed, not null | Email |
| `birth_date` | date, not null | Дата рождения |
| `city` | varchar(120), not null | Город |
| `created_at`, `updated_at` | timezone datetime | Временные отметки |

#### `products`

| Поле | Тип/ограничение | Смысл |
|---|---|---|
| `id` | PK integer | Идентификатор товара |
| `supplier_id` | FK `users.id`, indexed | Владелец-поставщик |
| `name` | varchar(255) | Название |
| `description` | nullable varchar(1000) | Описание |
| `price` | float | Цена единицы |
| `stocks` | integer | Агрегированный остаток по складам |
| `is_active` | boolean, default true | Признак доступности для покупки |
| `is_archived` | boolean, default false | Признак архива |
| `created_at` | timezone datetime | Время создания |

`total_price` не хранится: API рассчитывает его как округлённое до двух знаков `price * stocks`.

#### `warehouses`

Содержит `id`, название, строковый график по будням, адрес и время создания.

#### `warehouse_products`

Таблица связи склад–товар с составным PK (`warehouse_id`, `product_id`) и фактическим `stocks`. Агрегированный `products.stocks` пересчитывается как сумма всех этих строк.

#### `processed_events`

Содержит UUID события заказа и время обработки. Используется supplier consumer для дедупликации событий, у которых есть `event_id`.

#### `user_events` (`SupplierEvent`)

Создаётся audit-consumer. Хранит тип supplier-события, supplier ID в физической колонке `user_id`, JSON payload и время получения.

### 6.2. `customer_db`

#### `users` (`User`)

Покупатель: ID, полное имя, уникальный email, время создания. Связан с избранным, корзиной и заказами.

#### `products`

Локальная проекция supplier-товара: ID, название, описание, цена, агрегированный остаток, `is_active`, `is_archived`, исходное время создания. `supplier_id` в проекции не хранится.

#### `favorites`

Связь покупателя с товаром. Пара (`user_id`, `product_id`) уникальна. Есть собственный ID и время создания.

#### `cart_items`

Связь покупателя с товаром и количеством. Пара (`user_id`, `product_id`) уникальна. Цена в строке корзины не хранится и берётся из текущей проекции товара при выдаче ответа.

#### `orders`

Заказ хранит покупателя, уникальный nullable `order_number`, строковый статус, сохранённую общую стоимость и время создания. Реализация создаёт номера вида `ORD-000001` и статусы `created`/`cancelled`.

#### `order_items`

Позиция заказа хранит товар, количество, цену единицы и сумму позиции на момент создания заказа. При чтении вложенная краткая карточка товара всё равно строится по текущей записи `products`.

## 7. HTTP API

Все ошибки FastAPI обоих API приводятся к форме `{"error":{"code":"...","message":"..."}}`. Ошибки валидации возвращаются с HTTP 400. Необработанные исключения скрываются как `internal_error` с HTTP 500.

### 7.1. Supplier API (`:8000`)

| Метод и путь | Результат | Основные проверки/эффекты |
|---|---|---|
| `GET /health` | `{"status":"ok"}` | Не проверяет БД или Kafka |
| `POST /suppliers` | 201, supplier | Уникальность email/телефона; событие `SUPPLIER_CREATED` |
| `GET /suppliers` | `items + count` | Все записи по ID |
| `GET /suppliers/{id}` | supplier | 404 при отсутствии |
| `PUT /suppliers/{id}` | supplier | Частичное фактическое обновление через optional-поля; событие `SUPPLIER_UPDATED` |
| `DELETE /suppliers/{id}` | 204 | Запрещено при наличии товаров; событие `SUPPLIER_DELETED` |
| `POST /warehouses` | 201, warehouse | Создание склада |
| `GET /warehouses` | `items + count` | Все склады по ID |
| `GET /warehouses/{id}` | warehouse | 404 при отсутствии |
| `PUT /warehouses/{id}` | warehouse | Optional-поля позволяют частичное обновление |
| `DELETE /warehouses/{id}` | 204 | Удаляет складские строки, пересчитывает затронутые товары, публикует `STOCK_REPLENISHED` |
| `POST /products` | 201, product | Проверяет supplier и состояние; начальный stock = 0; `PRODUCT_CREATED` |
| `GET /products` | `items + count` | Все товары, включая неактивные/архивные |
| `GET /products/{id}` | product | Включает stocks и вычисленный total_price |
| `PUT /products/{id}` | product | Optional-поля; проверяет нового supplier и состояние; `PRODUCT_UPDATED` |
| `DELETE /products/{id}` | 204 | Физически не удаляет: active=false, archived=true; публикует `PRODUCT_UPDATED` |
| `POST /warehouses/{id}/stocks` | обновлённые товары | Устанавливает фактические остатки, а не прибавляет; пересчитывает сумму и публикует `STOCK_REPLENISHED` |

Supplier validation включает: длины строк, email, положительный supplier ID и цену, неотрицательный stock, непустое после trim имя товара. Телефон очищается от нецифровых символов, форма с `8` преобразуется в `+7`, итоговая форма — `+7` и десять цифр. Архивный товар не может одновременно быть активным.

### 7.2. Customer API (`:8001`)

| Метод и путь | Результат | Основные проверки/эффекты |
|---|---|---|
| `GET /health` | `{"status":"ok"}` | Не проверяет БД, Kafka или supplier-service |
| `POST /users` | 201, user | Уникальный email |
| `GET /users` | `items + count` | Все пользователи по ID |
| `GET /users/{id}` | user | 404 при отсутствии |
| `GET /products` | `items + count` | Вся локальная проекция без фильтра по флагам |
| `GET /products/{id}` | product | Товар из локальной проекции |
| `POST /favorites` | 201, favorite | Проверяет user/product; повторное добавление возвращает существующую запись и также имеет декларированный 201 |
| `GET /favorites?user_id=` | `items + count` | Проверяет пользователя |
| `DELETE /favorites/{product_id}?user_id=` | 204 | 404, если связи нет |
| `GET /cart?user_id=` | корзина и суммы | Цена и суммы вычисляются по текущей цене товара |
| `POST /cart` | 201, позиция | Проверяет флаги и доступный stock; для существующей позиции прибавляет quantity |
| `PATCH /cart/{product_id}` | позиция | Заменяет quantity; проверяет флаги и stock |
| `DELETE /cart/{product_id}?user_id=` | 204 | Удаляет позицию |
| `POST /orders` | 201, order | Берёт явные items либо корзину, агрегирует дубли, проверяет локальный каталог, сохраняет order, очищает всю корзину, публикует события |
| `POST /orders/{id}/cancel?user_id=` | order | Меняет `created` на `cancelled`; повторная отмена — 409 |
| `GET /orders?user_id=` | `items + count` | Заказы с непустым номером, новые первыми |
| `GET /orders/{id}?user_id=` | order | Заказ должен принадлежать пользователю |

`POST /orders` трактует `items=None` и `items=[]` одинаково: использует корзину. Если корзина пуста, возвращается `cart_is_empty`. Дубли product ID в явном массиве суммируются. Даже при создании заказа из явных items после успеха удаляются все строки корзины пользователя.

## 8. Kafka

### 8.1. Общие свойства

- брокер один, replication factor внутренних топиков равен 1;
- топики создаются автоматически;
- producer вызывает `produce()` и `poll(0)`, но не вызывает `flush()` и не задаёт callback доставки;
- все события получают `event_version=1`, если поле не задано;
- ключом событий поставщика/товара служит ID сущности, stock/order — product ID;
- consumers используют `auto.offset.reset=earliest`, отключённый auto commit и ручной commit после успешного вызова обработчика;
- каждый consumer пробует обработать сообщение до трёх раз с паузой в одну секунду;
- после исчерпания попыток сообщение только логируется как `dead letter`; отдельного DLQ-топика нет, offset не фиксируется в этой ветке обработки;
- при сбое внешнего цикла повторное подключение выполняется через пять секунд.

### 8.2. Топики и события

#### `supplier-events`

Producer: supplier-service. Consumer: audit-consumer. Типы:

- `SUPPLIER_CREATED`;
- `SUPPLIER_UPDATED`;
- `SUPPLIER_DELETED`.

Envelope: `event_type`, `payload`, `event_version`. Payload соответствует supplier API-модели и содержит ID, персональные поля и timestamps.

#### `product-events`

Producer: supplier-service. Consumer: customer-service. Фактически публикуются:

- `PRODUCT_CREATED`;
- `PRODUCT_UPDATED`, включая архивирование через DELETE.

Consumer также умеет обработать `PRODUCT_DELETED`, но supplier-service такой тип не публикует. Payload содержит supplier ID, карточку товара, агрегированный stock, вычисленный total price и время создания; customer-проекция сохраняет не все поля.

#### `product-stock-events`

Producer: supplier-service. Consumer: customer-service. Типы:

- `STOCK_REPLENISHED` — после установки складских остатков и после удаления склада;
- `STOCK_DECREASED_BY_ORDER` — после обработки заказа, если остаток действительно изменился.

Поля: `event_type`, `product_id`, `total_quantity`, `event_version`. Customer consumer для совместимости также читает поле `stocks`, если `total_quantity` отсутствует.

#### `order-events`

Producer: customer-service. Consumer: supplier-service. Тип `ORDER_CREATED`; поля: UUID `event_id`, `event_type`, `product_id`, `quantity`, `event_version`. На один заказ публикуется отдельное событие для каждого уникального товара, а Kafka key равен product ID.

### 8.3. Обработка заказа на стороне остатков

Supplier consumer:

1. принимает только `ORDER_CREATED`;
2. резервирует UUID в `processed_events` через `ON CONFLICT DO NOTHING`;
3. загружает складские строки товара в порядке `warehouse_id`, затем `product_id`;
4. последовательно уменьшает их до исчерпания заказанного количества или имеющегося stock;
5. пересчитывает `products.stocks` как сумму складских строк;
6. коммитит БД;
7. при фактическом изменении публикует `STOCK_DECREASED_BY_ORDER`.

Customer API предварительно проверяет количество по своей локальной проекции, но supplier consumer повторно не проверяет достаточность общей суммы и может списать только доступную часть. Статус заказа при этом не меняется и ответного события об успехе/неуспехе нет.

### 8.4. Синхронизация каталога

При старте customer-service делает HTTP GET полного supplier-каталога, upsert каждой записи и пытается удалить локальные товары, которых больше нет в ответе. Удаление может быть пропущено при нарушении FK из customer-таблиц. Архивированные товары supplier остаются в выдаче и поэтому синхронизируются как архивированные.

При stock-событии неизвестного товара customer-service запускает ту же полную синхронизацию, затем повторяет обновление stock. Та же ветка запускается и когда товар существует, но stock уже равен значению события, потому что функция возвращает `False` как при отсутствии, так и при отсутствии изменения.

## 9. Docker и запуск

Compose определяет восемь сервисов. PostgreSQL имеют healthcheck; приложения ожидают healthy DB и started Kafka. Customer дополнительно ожидает лишь started supplier-service. Kafka, API и consumers не имеют healthcheck в compose.

Персистентность обеспечивают named volumes `postgres_data` и `customer_postgres_data`. Исходный код внутрь контейнеров не монтируется: изменение требует rebuild. Сеть явно не задана и создаётся Compose автоматически.

Секреты для локальных БД заданы непосредственно в compose как `app/app`. TLS/SASL для Kafka не настроены. Kafka advertised listener использует внутреннее имя `kafka-broker:9092`; доступ UI идёт внутри compose-сети.

## 10. Жизненный цикл данных

### 10.1. Поставщик

Поставщик создаётся/обновляется в supplier DB, после commit публикуется событие, audit-consumer сохраняет отдельную JSON-копию события в той же БД. Удаление возможно только при отсутствии связанных товаров; перед физическим удалением формируется payload для аудита.

### 10.2. Товар

Товар создаётся у существующего supplier с нулевым stock. После commit событие асинхронно создаёт customer-проекцию. Изменение карточки также переносится событием. DELETE переводит товар в `inactive + archived`; физическая строка и остатки остаются. Customer consumer обновляет флаги и тем самым блокирует добавление/покупку после доставки события.

### 10.3. Остаток

Запрос к складу устанавливает абсолютное количество по паре склад–товар. Supplier пересчитывает агрегат и публикует его. Customer сохраняет только агрегат. Удаление склада удаляет его строки, пересчитывает товары и публикует событие с тем же именем `STOCK_REPLENISHED`, даже если итоговый stock уменьшился.

### 10.4. Корзина и заказ

Корзина проверяется относительно текущей customer-проекции. Создание заказа фиксирует цены, создаёт номер, очищает корзину и коммитит customer DB. Только затем события заказа ставятся в Kafka. Supplier асинхронно списывает складские строки и сообщает новый агрегат обратно customer-service. Поэтому сразу после HTTP 201 stock в обеих выдачах может временно различаться, а успешный заказ уже существует до фактического списания supplier stock.

### 10.5. Отмена

Отмена меняет только строковый статус customer-заказа на `cancelled`. Kafka-событие не публикуется, supplier stock не возвращается, корзина не восстанавливается.

## 11. Основные пользовательские сценарии

1. Оператор supplier API создаёт поставщика, склад, товар и задаёт складской остаток.
2. Покупатель появляется в customer-service как пользователь с именем и email.
3. Покупатель просматривает локальный каталог после его асинхронной/стартовой синхронизации.
4. Покупатель добавляет и удаляет товар из избранного; повторное добавление идемпотентно на уровне записи.
5. Покупатель добавляет товар в корзину, увеличивает количество повторным POST, заменяет количество PATCH или удаляет позицию.
6. Покупатель создаёт заказ из корзины либо явно переданных позиций.
7. Покупатель просматривает список/детали своих заказов и может отменить неотменённый заказ.
8. Архивный или неактивный товар остаётся видимым в каталоге, но блокируется при добавлении в корзину и оформлении заказа.

## 12. Основные технические сценарии

- создание/обновление supplier-схемы и customer-схемы при старте приложений;
- полная HTTP-сверка customer-каталога с supplier-каталогом;
- event-driven upsert карточки товара;
- отдельное event-driven обновление stock;
- идемпотентная обработка order event по UUID в supplier-service;
- последовательное списание товара со складов по возрастанию ID склада;
- аудит supplier events в общей supplier DB;
- retry consumer-обработки и логирование необработанного сообщения;
- единая упаковка HTTP-ошибок для каждого API.

## 13. Подтверждённые бизнес-правила

### Поставщики и склады

- email и телефон supplier уникальны;
- телефон нормализуется в российский формат `+7XXXXXXXXXX`;
- supplier нельзя удалить, пока у него существует хотя бы один товар, включая архивный;
- складские данные задаются как фактическое абсолютное количество;
- один товар может иметь остатки на нескольких складах;
- удаление склада уменьшает агрегат на остатки удалённых строк.

### Товары

- supplier товара должен существовать;
- trimmed name не может быть пустым, цена должна быть больше нуля;
- складской и агрегированный stock не допускаются отрицательными через публичные входные схемы;
- состояние `is_archived=true, is_active=true` отклоняется;
- физического удаления товара через API нет;
- неактивный и архивный товар видим в обоих каталогах;
- архивный или неактивный товар нельзя положить в корзину или заказать.

### Избранное и корзина

- операции требуют существующего пользователя и локального товара;
- одна пара user–product имеет не более одной favorite и одной cart item;
- favorites не участвует в корзине/заказе;
- повторный POST favorite возвращает имеющуюся запись;
- повторный POST cart прибавляет количество;
- PATCH cart заменяет количество;
- количество должно быть больше нуля и не выше локального агрегированного stock.

### Заказы

- заказ формируется из непустого явного `items` либо из корзины;
- одинаковые товары в явном `items` агрегируются;
- каждый товар повторно проверяется на существование, состояние и локальный stock;
- цены позиции и заказа фиксируются при создании;
- после успешного commit очищается вся корзина пользователя;
- начальный статус — `created`, доступный переход API — в `cancelled`;
- повторная отмена запрещена;
- отмена не возвращает stock;
- заказ доступен только при совпадении `user_id`.

## 14. Найденные зависимости

- supplier-service зависит от supplier PostgreSQL и Kafka; Python: FastAPI, Uvicorn, SQLAlchemy, psycopg, confluent-kafka, email-validator.
- customer-service зависит от customer PostgreSQL, Kafka и HTTP supplier-service; набор Python-зависимостей совпадает с supplier-service.
- audit-consumer зависит от supplier PostgreSQL и Kafka; FastAPI/Uvicorn/Pydantic ему не нужны.
- customer favorites/cart/orders через FK зависят от существования локальной product-проекции.
- supplier product зависит от supplier, warehouse-product — от warehouse и product.
- сериализация customer favorite, cart и order зависит от доступности текущей product-записи.
- корректность stock-проверок customer-сценариев зависит от своевременности Kafka/HTTP-синхронизации.

## 15. Найденные ограничения

- система предназначена для локального ручного тестирования, а не production deployment;
- аутентификация и авторизация отсутствуют; принадлежность задаётся входным `user_id`;
- нет оплаты, доставки и внешних marketplace-интеграций;
- consistency между каталогом/остатками eventual;
- нет распределённой транзакции между customer DB, Kafka и supplier DB;
- события публикуются после DB commit без outbox;
- подтверждение доставки producer не контролируется;
- нет формального реестра/схемы событий и контроля совместимости `event_version`;
- нет отдельной DLQ, мониторинга, метрик и трассировки;
- один Kafka broker и один экземпляр каждого сервиса описаны compose;
- миграции заменены runtime `create_all` и точечными `ALTER TABLE`;
- пагинация, фильтрация и сортировка API почти отсутствуют;
- денежные значения хранятся как floating point;
- отмена заказа не компенсирует остатки;
- supplier не подтверждает customer-service полное или частичное списание;
- stock может быть проверен по устаревшей customer-проекции;
- README и код не описывают конкурентное оформление заказов;
- Postman-коллекции, на которые ссылается служебный YAML, не находятся в репозитории.

## 16. Реализованные архитектурные решения

- разделение supplier/customer на отдельные сервисы и отдельные БД;
- локальная customer-проекция каталога вместо чтения supplier API на каждый запрос;
- Kafka как основной транспорт доменных изменений и заказов;
- HTTP snapshot-sync как дополнение к потоку событий;
- агрегированный stock хранится денормализованно в supplier product и customer product;
- складские остатки сохраняются отдельно только в supplier-домене;
- архивирование товара вместо удаления;
- audit consumer отделён от supplier API, но пишет в его БД;
- ручной commit Kafka offsets после обработки;
- UUID-дедупликация только для order events;
- единый формат HTTP-ошибки внутри обоих API;
- API-модели ответа собираются явно, а не всегда возвращают ORM-модели напрямую.

Эти пункты фиксируют существующую реализацию и не являются оценкой или предложением её изменить.
